# 红鸢「书籍化」架构 — 一轮思索的完整记录

> 这是一份**决策过程记录**，不是终版设计文档（终版见《书籍化Skills管线-架构设计.md》）。
> 记录同一轮里三次质疑、三次修正的完整轨迹，以及最终沉淀下来的判断。

---

## 缘起

用户给出三份文档（WorkBuddy 首次思索 / GPT 思索 / GPT 后拉仓库的接线方案），核心诉求是：

> 「判断和研究我们如何搭自己的 skills 管线，**绝对不能直接把现有 skills 全部拉取接上**，而是针对项目研究，架构一套 skills 匹配多 agent 流程来做内容，以内容品质为导向，尽量减缓 token 消耗。」

约束很明确：不照搬现成 skills、内容品质优先、省 token、工程严谨。

但**这条诉求本身埋着一个陷阱**——它预设了「skills + 多 agent」这个解法。三轮迭代，本质上就是在拆解这个预设，最后发现连「skills」「多 agent」本身都不需要。

---

## 核心问题

我们真正要解决的不是「怎么装 skills」，而是：

> **把 RedTrip 的 city-walk 内容（路线 + 溯源叙事）做成一本「书」的形态。**

认清这个本质后，每一轮的修正都是「砍掉一层不必要的抽象」。

---

## 第一版：四层流水线（被否）

我最初的方案，把架构画成五层线性流水线：

```
L0 数据层 → L1 取证层 → L2 叙事层 → L3 书籍化层 → L4 编排层(skill)
```

**用户质疑 1**：「叙事层和书籍化层、编排层的说法是不是太沿用之前的强加了，存不存在优化？」

**我的诊断**（两个真实错误）：

1. **「叙事 → 书籍化」排成流水线是错的**。叙事（`narrative.py` + `polish.py` 产出 story_card）是**内容生产**；书籍化（目录/脚注/colophon/导出）是**呈现**。二者正交，不是前后工序。把它们串成 L2→L3，暗示「先写完再装订」，但出版引擎只依赖「溯源叙事」这个契约、不依赖叙事实现——本该解耦。
2. **「编排层」是概念强加**。①编排功能 `pipeline.py` 早就是编排器，再立「编排层」是重复；②skill 是 WorkBuddy 的运行时入口，不是 RedTrip 系统的内部层，塞进内部分层是层次混淆。

---

## 第二版：可信度轴 × 形态轴（被否）

我修正为围绕 RedTrip 本质的两条正交轴：

```
可信度轴（证据 → 溯源 → 门禁，贯穿不变）
形态轴（同一溯源叙事 → 路线页 / 书 / PPT，可插拔）
```

落成三概念：内容管线（已有）+ 出版引擎 `book.py`（新增）+ `redtrip-book` skill（外部 facade）。

**用户质疑 2**：「一个 agent 里内置一个编排层多 agent 系统怪怪的，能不能不用 agent 和 skills？」

**我的诊断**（skill 那套也是过度设计）：

1. **套娃**：WorkBuddy 本身就是一个 agent 运行时，在它内部再「内置编排层 + 多 agent 系统」，是 agent 里套 agent 编排。
2. **不需要自主性**：书籍化是「把结构化 JSON 变成另一种结构化呈现」的确定性机械转换。agent 的价值在自主决策，这里没有决策、只有映射。硬上 agent 反而危险——agent 自由发挥 = 幻觉 = 破坏溯源。
3. **skill 是开发期工具，不是产品架构**：skill 是 AI 助手协调用的，不该进入 RedTrip 产品运行时的架构。

---

## 第三版（终版）：渲染器模式（纯软件）

砍掉 skill、agent、编排层后，剩下最诚实的架构：

```
入口：/v1/book · python -m redtrip_curator.book（普通 API/CLI）

内容管线（已有 · 唯一真身 · 证据先于叙事）
  intent → evidence → plan → narrative → polish → gate
  产出 envelope「溯源叙事」= StoryChapter[] + EvidenceGraph + ProvenanceReport
        ├── render_web()    → 路线页（已有）
        ├── render_book()   → 书（新增 · 纯函数）
        └── render_…()      → 未来形态（PPT / 展板…）

序/引子/桥 = envelope 里的额外章节，走同一 narrative→polish→gate（可选）
```

新增物只有三样，**没有一个是「层」**：

| 新增物 | 是什么 | token |
|---|---|---|
| `render_book(envelope)` | 纯函数，消费「溯源叙事」契约 → 目录/脚注/colophon/HTML | 零 |
| `/v1/book` + CLI | 普通 endpoint + `python -m redtrip_curator.book` | 零 |
| `compose_frontmatter()`（可选） | 序/引子/桥 = 额外章节，走同一 narrative→polish→gate | 受控 |

**为什么这一版站得住**：书只是「溯源叙事」这个稳定契约的又一个渲染目标，跟现有 `render_web` 平级。RedTrip 现在 `/v1/curate` 产 envelope 给前端渲染，书籍化 = 加一个平行的 `render_book` + 一个平行的 endpoint，仅此而已。

---

## 沉淀下来的判断（可复用认知）

1. **RedTrip 的本质是「证据约束的叙事生成器」**。evidence-first 是灵魂，任何架构若不以此为核心、而以通用分层为轴，就是强加。

2. **「内容生产」与「呈现」是两个正交关切**。内容管线产出「溯源叙事」契约，渲染器把它映射成各种形态（路线页 / 书 / PPT）。二者单向依赖、契约解耦——将来叙事层换成多 agent，渲染器一行不用改。

3. **书籍化 = 确定性数据转换 + 渲染，属于 MVC 的 View 层**。不需要 agent 的自主性，纯函数 + 模板渲染即可。

4. **多 agent 若真需要，只在「策划阶段」**（意图理解 / 命题策划 / 用户研究），是内容管线之前的输入准备，不在装订阶段。

5. **skill / agent 是开发期工具，不进产品运行时**。产品能力用纯代码（函数 + 管线 + 渲染器）实现。

6. **每一轮都在「砍」**。五层 → 三概念 → 三样新增物。砍掉的都是过度设计，不是功能。省 token 的最终答案不是「更聪明的 agent」，而是「根本不用 agent」。

---

## 一页纸终版

- **不改**：内容管线（`intent → evidence → plan → narrative → polish → gate`）。
- **新增**：一个纯函数 `render_book()`、一个 endpoint `/v1/book` + CLI、可选 `compose_frontmatter()`。
- **删除**：一切 skill / agent / 编排层的设计。
- **红线**：绝不叠加「全书 LLM 重写」；溯源全程保留；排版零 token。
