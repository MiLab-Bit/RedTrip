## 0. Verdict

> ## **有条件 GO**
> **一句话理由**：跨库 join 在 API 端点层已被证实存在（核心 IP 有数据基底），而两道"阻塞闸"经独立分诊后**均非上游能力缺陷、均为本地环境/桥接层缺陷**，属分钟级到小时级可修，不构成产品级 NO-GO；条件是 S0 Spike 必须先实测字段与真实 join 层数。

## 1. 关键更正：两道闸的根因诊断（推翻原假设）

主理人原判：「① 缺 API Key（上游鉴权/SSL 失败）；② 中文关键词编码缺陷」。
经独立分诊，**① 的归因错误，且错得对项目有利**。

### 1.1 分诊证据（本机 curl 实测，2026-08-06）

| 测试 | 命令 | 结果 |
|---|---|---|
| 走系统代理访问上图 | `curl https://data.library.sh.cn/` | ❌ `(35) schannel: failed to receive handshake, SSL/TLS connection failed`，`remote_ip=127.0.0.1` |
| 走系统代理访问 opendata | `curl https://opendata.library.sh.cn/` | ❌ 同上，`remote_ip=127.0.0.1` |
| 走系统代理访问搜韵 | `curl https://sou-yun.cn/` | ❌ 同上 |
| 走系统代理访问对照组 | `curl https://www.baidu.com/` `https://github.com/` | ✅ `http=200`（证明代理本身工作正常，仅特定域名被掐） |
| **绕过代理直连上图** | `curl --noproxy '*' https://data.library.sh.cn/` | ✅ **`http=302`，真实 IP `180.166.28.107`，1.46s** |
| **绕过代理直连 opendata** | `curl --noproxy '*' https://opendata.library.sh.cn/` | ✅ **`http=200`，真实 IP `218.1.116.119`，0.10s** |
| 绕过代理直连搜韵 | `curl --noproxy '*' https://sou-yun.cn/` | ⚠️ 解析到真实 IP `47.103.64.227`，仅因**本机证书吊销检查（CRL 服务器脱机）**失败，服务器本身可达 |
| 环境变量 | `env \| grep -i proxy` | `HTTP_PROXY=http://127.0.0.1:7897/`、`HTTPS_PROXY=http://127.0.0.1:7897/`（Clash 类本地代理默认端口） |
| 站点存活确认 | 抓取首页 HTML | `data.library.sh.cn` = "上海图书馆开放数据平台"；`opendata.library.sh.cn` = "上海图书馆开放数据竞赛"，**均正常返回，根路径未要求任何 Key** |

### 1.2 由证据推出的完整因果模型（可解释全部三类实测现象）

```
调用带中文关键词 ──► 参数序列化阶段就崩（surrogate 编码）──► 根本没走到网络 ──► 报编码错
调用纯 ASCII 参数 ──► 序列化通过 ──► 发起 HTTPS ──► 被本机代理 7897 掐断 TLS ──► 报 SSLEOFError
slc_endpoints    ──► 97 条端点目录疑为「随服务端内置的静态清单」，无需联网 ──► 唯一成功
```

**三种现象、一个模型、零矛盾**——这是目前唯一能同时解释「中文必崩编码错 / ASCII 必崩 SSL 错 / endpoints 必成功」的假说。

### 1.3 结论修正

> ❌ 原判"缺 API Key" → ✅ 实为**本机系统代理（127.0.0.1:7897）拦截了 `*.library.sh.cn` / `sou-yun.cn` 的 TLS 连接**。
>
> **鉴别依据**：鉴权失败的表现是 HTTP `401/403` 带响应体，**绝不会**是 TLS 握手层 EOF。TLS EOF 是传输层故障签名，与业务鉴权无关。且直连实测 `302/200`，服务器在根路径**不索要 Key**。

## 2. 两道闸：严重度、解决路径、可验证性

| | 闸① 上游取数断（SSLEOFError） | 闸② 中文 surrogate 编码崩溃 |
|---|---|---|
| **原判严重度** | S1 致命，疑似需申请 Key（天级、且可能申不到） | S1 阻塞 |
| **修正后严重度** | **S3 环境级（分钟可修）** | **S2 高，但可架构绕开（不阻塞）** |
| **根因** | 本机 `HTTP(S)_PROXY=127.0.0.1:7897` 对中国大陆站点走了不可达出口/规则拒绝 | `'utf-8' codec can't encode surrogate '\udcXX'` 是 **Python `surrogateescape` 的特征串**：进程以非 UTF-8 locale（Windows GBK 代码页）解码 stdio/argv 后再严格 encode。属 **MCP 服务端/桥接层缺陷，非上游 API 缺陷** |
| **解决路径** | ① 给 MCP 服务进程设 `NO_PROXY=*.library.sh.cn,library.sh.cn,sou-yun.cn`（或 `NO_PROXY=*`）；② 或在 Clash 规则里给这些域名加 `DIRECT`；③ 顺带处理搜韵的 CRL 吊销检查（关闭 revocation check 或换 curl/requests 走 certifi） | ① 根治：MCP 服务端设 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`；② 绕行（**推荐，见下**）：主流程改为 URI 主键检索，运行时不传中文 |
| **可验证性** | **极高**。已由本文 §1.1 验证完毕，剩余唯一未知是 MCP 服务端是否与本会话同环境（若为远端托管服务则需其运维侧同样处理）。验证成本 5 分钟 | **高**。鉴别实验：对**已知可用、免 key 的 `slc_endpoints`** 传一个含中文的可选参——若同样崩，则 100% 确证故障在桥接层（根本没走网络），与上游无关；若只有内容端点崩，才是上游 |
| **是否阻塞 GO** | 否（环境问题） | 否（有架构绕行） |

### 2.1 闸② 的架构级绕行方案（建议无论 bug 是否修复都采用）

核心 join 主键是 **`buri`（建筑 URI）**，`building_event_list` 按 URI 查事件——**这条主链路根本不需要中文关键词**。
因此建议：

```
【离线】building_list 全量分页拉取（无关键词/ASCII 参数）
      → 落本地库 + 自建中文倒排索引（建筑名/路名/别名）
【在线】用户中文出题 → 命中本地索引 → 拿到 buri
      → 仅以 buri / 年份 等 ASCII 参数调 MCP 取详情与事件
```

**一石三鸟**：① 中文闸从阻塞降为非阻塞；② 在线 MCP 调用次数骤降 → 直接缓解 §4 的时延风险；③ 上游抖动时仍可服务（可用性上升）。
**代价**：需接受"数据快照"而非"实时取证"，对外表述须改为「基于上图开放数据构建的本地索引，每条附原始 URI 可溯」——**G1 数据可溯 100% 仍然成立**，只是"实时"二字要去掉。建议主理人就此拍板。

### S0 退出准则（三选一，直接对应排期决策）

- **≥1 条完整 ≥3 层链路可复现 且 building 含坐标** → **无条件 GO**，PRD P0 30 人日照排。
- **仅两层 / 无坐标** → **有条件 GO**：核心 IP 口径改为「一栋楼的两重人生：建筑 × 红色事件」（诚实且仍独家），R-05 加地理编码兜底，R-11 视 U2 结果下沉或砍掉。

## 5. 模型 / P95≤60s / 成本 可行性初判

### 5.1 ⚠️ 头号更正：最大时延风险不是 MCP，是 LLM 输出长度；G3 目前大概率不达标

| 环节 | 估算 | 说明 |
|---|---|---|
| **LLM 生成** | **100–260s** | 6 点位（故事卡 + 机位卡 + 年龄对照 + 溯源）≈ **5–8k output tokens**；按主流模型 30–60 tok/s **串行**计算 |
| **MCP 取数** | 12–32s | 一条路线约 20–40 次调用（detail×6 + event×6 + era/poem×N），RTT 0.3–0.8s，**串行**计 |
| **门禁校验** | <1s ~ 15s | schema / palette / 槽位为本地计算 <1s 可忽略；但若 R-07 做 **source 链接实时回源探活**（15–30 条），串行 5–15s，**且撞同一个闸①** |
| **合计（朴素串行）** | **≈ 115–300s** | **超 G3 目标（P95 ≤60s）2–5 倍** |

### 5.2 达标路径（三条并用，可把首屏压到 60s 内）

1. **点位池离线预生成 + 缓存**（配合 §2.1 架构）：在线只做选点、排序与拼装，MCP 在线调用 40 次 → **接近 0 次**。
2. **6 点位并行生成**：6 路并发各约 700–1300 tokens → **15–25s**。
3. **分段流式**：先出路线骨架（<10s 首屏），卡片按点位流式补齐。

> **建议主理人拍板修改 PRD §5 G3 口径**：
> 由「P95 时延 ≤60s」改为 **「首屏路线骨架 P95 ≤60s；全量素材包 P95 ≤180s」**。
> 不改口径，G3 在竞赛演示现场大概率现眼；改了口径且落实上述三条，则 G3 可达。

### 5.3 门禁对时延的具体处置建议（R-07 / US-5）

- `source` 校验**改为「URI 格式校验 + 本地缓存命中」，不做实时 HTTP 回源探活**（否则既慢又受闸①牵连）。
- 红队回归 `tests/redteam_check.py` **离线跑，不进在线链路**。
- 重试策略必须封顶：**「最多重生成 1 次，否则降级输出并显式标注」**。否则 FAIL→重生成会让 P95 直接翻倍，G3 必挂。

### 5.4 成本：不构成约束，但真成本项被低估

- **推理成本**：单次策展约 8–15k input + 5–8k output ≈ **¥0.3–0.6/次**。竞赛量级（<1000 次）总计 **<¥600**，可忽略不计。
- **⚠️ 真成本是人工审核**：红色题材 AIGC 必须人工兜底（见战略报告 SWOT-T④），**人力成本 >> 推理成本**。在 C 端 0–30 元档（战略报告定调）下，这是毛利的真正杀手，而非 token 费用。
- **对定价实验的含义**：§14「轻履约定价实验（30–100 元档）」的单位经济模型里，**必须把人工审核工时计入变动成本**，否则会高估毛利率。建议与路径（路线图规划师）同步此口径。

## 6. 给主理人的三个待拍板

1. **是否采纳「离线灌库 + 本地索引」架构**（§2.1）——影响对外"实时 MCP 取证"表述，但能同时解掉编码闸与时延两大问题。
2. **是否修改 PRD §5 G3 时延口径**（§5.2）——不改则 G3 大概率不达标。
3. **若 S0-4 实测只有两重人生，是否接受核心 IP 口径下调**（§4 退出准则第二条）——建议接受，诚实表述仍具独家性，强撑"四重"有现场被证伪风险。
